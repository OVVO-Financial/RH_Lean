# Lossless agent-report publication and recovery — 2026-11-18

**REPORT_PUBLISH_RECOVERY_V1 — mandatory for all seven RH_Lean roles after reviewed human merge into main.** This is a reporting safeguard, not a mathematical theorem, new agent run, Studio prompt update, tool grant, direct-main permission, PR authorization, or autonomous merge. Existing report ownership and the [latest-actual-report continuity rule](RHLEAN_REPORT_CONTINUITY_LAST_ACTUAL_20261111.md) remain in force. Reports are written to the `agent-reports` branch, not `main`.

## Incident and scope

The 2026-11-18 Adversarial Referee could not publish: direct Git transport returned **HTTP 403 at the tunnel**, and a connected writer supported complete replacement rather than append. The pinned `agent-reports` report `research/agent_reports/2026-11-18/50-adversarial-referee.md` was **118,316 bytes** at commit `2457a0f73b97e6154d1ea65f4b8ea0ca3f1dc1cd`. Since the agent could not retrieve and verify all prior bytes, it correctly refused to replace the existing record with an excerpt. The local unpublished report is not thereby published. A tunnel-level 403 does **not** establish that authenticated GitHub API write access is unavailable.

## Required safe-publication algorithm

1. **Checkpoint first.** Save the complete new report/checkpoint/resume capsule locally before transport. Record the actual invocation timestamp and America/New_York offset, observed trigger, actual run ID or `RUN_ID_UNAVAILABLE`, a unique section marker, main/policy/source SHAs and the **live** `agent-reports` branch HEAD. Do not use an old pinned commit as an unconditional update base.
2. **Read and validate the complete remote history.** For an existing canonical role file, request its entire contents at `ref=agent-reports` using authenticated GitHub Contents API; if necessary fetch the Git blob by SHA, or reconstruct every ordered chunk. Verify **UTF-8 byte length** and Git blob SHA computed over `b"blob <byte-length>\0" + exact_bytes`, plus the provider's object metadata. A line-limited fetch, summary, old checkpoint tail or truncated response cannot be used to reconstruct a replacement body. If the canonical path does not exist, create it with the new full payload.
3. **Append safely, even with a replacement-only writer.** Preserve the exact old bytes and append the **entire** new section once; submit the complete old-plus-new UTF-8 file with the freshly observed blob SHA as a compare-and-swap guard. If another writer advanced the file, refetch all bytes, search for the unique section marker, reconcile and retry **once**. Never force-push, destroy corrections/history, reuse an obsolete blob SHA or duplicate an invocation.
4. **Change transport after a tunnel error.** On direct Git `HTTP 403` at the tunnel, do not repeatedly retry that same channel. Where the role's current authenticated connection offers it, use GitHub Contents create/update API or an authorized Git blob/tree/commit/ref route guarded by the live head. Record a genuine repository/API permission failure separately from tunnel failure. Instructions cannot conjure missing tools or confer new permissions.
5. **Recovery instead of destructive replacement.** If the entire canonical file still cannot be verified or written safely, but authenticated **create-file** is available, publish the **full new payload** as an immutable, role-owned sibling continuation in the same dated report directory, with the filename `<owned-canonical-stem>.recovery-<UTC-timestamp>-<unique-id>.md` (e.g. `50-adversarial-referee.recovery-20261119T020000Z-<id>.md`). Use **create-only** semantics; never overwrite an existing recovery file. Include intended canonical path; original run ID/time; reason for fallback; observed base commit/blob SHA/byte length or `UNVERIFIED`; full substantive result; and resume capsule. Only the role's existing assigned filename stem(s) may have recovery siblings. **A recovery file does not mean the canonical file was appended.** If no authorized create-file path works, keep the local checkpoint and `NOT_PUBLISHED`.
6. **Coordinator mirror safety.** The existing `00-coordinator-am.md` and `90-coordinator-pm.md` canonical reports must be complete byte-identical mirrors. When possible, update them atomically in one authorized Git-data commit. If that is unsafe, create a *pair* of byte-identical owned `00-coordinator-am.recovery-...` and `90-coordinator-pm.recovery-...` files. A single successful side is `PARTIAL_MIRROR_DEFECT`, not a completed publication. Do not repair either mirror by guessing its history.
7. **Require independent remote readback.** Capture commit SHA, branch, file path, blob SHA and UTF-8 byte length. Read the result by its **exact commit SHA** and verify complete bytes/hash and unique section marker. For canonical append confirm all original bytes remain an unchanged prefix and the new section appears exactly once; for recovery confirm the immutable sibling contains the **entire** new payload and provenance. A successful API request without readback, unattached blob, local patch or inferred branch update is not a publication receipt.
8. **Report statuses exactly.** Only a readback-verified canonical append is `PUBLICATION=CANONICAL_VERIFIED`. A readback-verified owned sibling is `PUBLICATION=RECOVERY_VERIFIED; CANONICAL=NOT_UPDATED`. A possible remote write without confirmed readback is `PUBLICATION=REMOTE_COMMIT_UNVERIFIED`; if nothing was verified, use `PUBLICATION=NOT_PUBLISHED` with exact blocker and retained local checkpoint. Keep these separate from `EXECUTION_COMPLETED`, mathematical acceptance, independent review and PR/CI states.
9. **Resume and consolidate without double counting.** On the next actual invocation, find **all** canonical and verified own-role `.recovery-` siblings in the relevant dated folders (without a day cutoff), order by real invocation marker and commit, and backfill all unconsumed actual sections. If safe, append a recovery's unique section to the canonical record once and cross-reference the recovery SHA. Do **not** delete or rewrite the immutable recovery, claim it was previously canonical, fabricate a run, or count it again after consolidation.

Before claiming `publish_ack=REPORT_PUBLISH_RECOVERY_V1`, explicitly apply these scenarios:

- **118,316-byte replacement:** never publish an 8 KB summary, partial tail or unverified old record as the full report.
- **Tunnel 403:** test a separately authorized authenticated GitHub API operation; do not automatically label it a repository permission denial.
- **Concurrent updates:** stale blob SHA must lead to complete refetch and one reconcile/retry, not lost history or duplicated sections.
- **No complete original:** publish only a new full owned recovery sibling and verify its commit, or mark `NOT_PUBLISHED` if even that is unavailable.
- **Coordinator one-sided write:** missing/unequal `00`/`90` canonical or recovery mirrors cannot be marked fully published.
- **Later discovery:** include verified recovery files in the latest-actual ledger and consume them exactly once, including older dates, without backdating executions.
